# Stage 5 — Task Workflow, Audit History & Reassignment

Дата: 2026-11-05. Реализован только Stage 5; ручные UI-смоуки выполняет пользователь.

## Реализовано

- Ровно пять переходов из ТЗ, проверка роли через profiles и назначения через
  assignee_id. Manager не выполняет действия executor, accepted терминальный.
- Переходы и переназначение блокируют одну строку tasks через FOR UPDATE.
  Внутри SQL-транзакции проверяется уже заблокированное актуальное состояние.
- Возврат rework требует хотя бы одного непробельного символа (проверяются
  пробелы, табы и переводы строк). UI даёт комментарий только для этого действия.
- create_task записывает NULL → new; transition_task — старый/новый статус,
  actor=auth.uid(), server-side время и комментарий в той же транзакции.
- reassign_task проверяет manager и новый профиль executor, сохраняет статус
  и историю при любом статусе, включая accepted. Повтор того же назначения
  возвращает текущую запись без UPDATE; отдельного аудита назначений нет.
- История доступна по видимости задачи и закрыта для клиентских изменений.
  Старый исполнитель теряет доступ при новых запросах, новый получает всю историю.
- Карточка задачи: разрешённые действия, форма возврата, история с actor UUID/«Вы»,
  выбор нового исполнителя для manager. Применены существующие Button/Select/Table.
- Общий mutation-key для команд одной задачи блокирует повторную отправку
  и одновременную отправку перехода/переназначения из текущей карточки.
  Оптимистичных статусов нет; mutation retry выключен. После успеха и ошибки
  инвалидируются crm-ключи. Конфликт показывает ошибку, перечитывает данные
  и оставляет кнопку ручного обновления.

## SQL-функции и RLS

Новая миграция: `supabase/migrations/20261105030000_task_workflow.sql`.
Предыдущие миграции не изменялись. Таблицы, FK, CHECK и индексы сохранены.

| Функция | Операция | Проверки |
| --- | --- | --- |
| create_task (CREATE OR REPLACE) | Создание + первоначальная история | manager, существующий executor с блокировкой профиля, служебные поля задаёт БД |
| transition_task(uuid,text,text) | Статус + одно событие | auth.uid, профиль, FOR UPDATE, роль/назначение, матрица, комментарий |
| reassign_task(uuid,uuid) | Только assignee_id | manager, FOR UPDATE, существующий executor, no-op для прежнего ID |

Все три функции SECURITY DEFINER, owner явно postgres, search_path='',
полные имена объектов, без dynamic SQL. EXECUTE отозван у PUBLIC/anon,
authenticated проходит проверку внутри функции. Состояние владельцев и прав
проверено не предположением, а запросом каталогов PostgreSQL.

task_status_history: RLS сохранён, все прежние клиентские grants отозваны,
authenticated получает только SELECT. Policy `history_select_visible_task`:

```sql
using (exists (select 1 from public.tasks t where t.id = task_id))
```

Она опирается на уже работающий tasks RLS: manager читает всё, executor — только
назначенное, без профиля строки не видны. Цепочка history → tasks → profiles
ациклична. Прямой I/U/D/TRUNCATE истории и PATCH status/assignee_id не разрешены.
Каскадное удаление по прежним FK работает без клиентского DELETE истории.

Время события берётся clock_timestamp() после получения блокировки, а не из
начала транзакции, которая могла ждать. Чтение сортируется created_at ASC,
id ASC как детерминированный дополнительный ключ. Для старых задач начальное
событие может отсутствовать; фиктивный backfill не выполнялся.

## Найденные и устранённые проблемы

- Исторические режимы тестов больше не получают миграции будущих этапов:
  baseline 3A/3B отделены от полной схемы Stage 5, текущий CRUD дополнительно
  прогоняется на полной схеме перед workflow.
- Для аудита не используется transaction-start now(): событие после ожидания
  блокировки получает фактическое server-side время записи clock_timestamp().
- После ошибки команды UI автоматически перечитывает актуальный статус и историю,
  не закрепляет неподтверждённый статус и не повторяет неидемпотентную команду.
- Безусловный UPDATE при повторном назначении исключён, что проверено по xmin.
- Все исполнители действий в истории формируются сервером, не из формы/metadata.

Падающих тестов реализации в этом этапе не было. Эти пункты описывают устранённые
риски при реализации, а не ранее наблюдавшиеся production-инциденты.

## Ручной smoke checklist — максимум 5 сценариев

Перед проверкой применить локально `npx supabase migration up`; reset не требуется.

1. Manager создаёт объект и задачу для A: new и начальное NULL → new с автором
   manager. A берёт в работу и отправляет на проверку; manager видит историю.
2. Manager пытается вернуть без текста/с пробелами — форма не отправляется;
   затем возвращает с комментарием. A возвращает в работу и снова сдаёт,
   manager принимает. История содержит весь цикл, accepted без кнопок переходов.
3. Manager переназначает принятую задачу A → B и повторяет то же назначение:
   статус/история не меняются; после обновления A теряет карточку и историю,
   B видит задачу и прежние события. Элементов переназначения у executor нет.
4. Открыть новую задачу A в двух вкладках, конкурирующе взять в работу:
   одна команда проходит, вторая сообщает конфликт/обновляет данные; одного
   события достаточно. Проверить loading, disabled кнопки и ошибку сети с повтором.
5. Manager удаляет задачу с историей, затем объект с другими задачами, подтверждая
   действия. Списки обновляются, удалённые карточки недоступны; проверить таблицу
   истории и формы на мобильной ширине (горизонтальный скролл таблицы внутри блока).

## Известные ограничения

- Старые задачи могут не иметь NULL → new, backfill не выполняется.
- Без Realtime уже загруженный кеш другого браузера не стирается дистанционно;
  при каждом новом запросе доступ контролирует БД. Refetch/фокус/перезагрузка
  обновляют видимость. Уже прочитанные данные невозможно «отозвать» из памяти.
- После сетевого таймаута исход команды может быть неизвестен клиенту: UI
  перечитывает состояние, автоматически повторять переход не пытается.
- Нет отдельного аудита назначений/редактирования, произвольных комментариев UI,
  уведомлений, пагинации и новой дизайн-системы. Actor показан UUID или «Вы».
- История защищена от клиентского API; доверенный администратор БД остаётся
  административным контуром, как и в предыдущих этапах.
- Build успешен с предупреждением Vite о chunk 673.06 KB (gzip 201.03 KB).
  Лимит не подавлялся. Повторный lint последнего расширения Node-теста не разрешён.
- Ручной UI-smoke выполняет пользователь. Коммита, деплоя и следующего этапа нет.
