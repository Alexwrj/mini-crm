# Решения, допущения и ограничения

Актуально для реализации после Stage 5 и до публикации. Правила из ТЗ и ответы
заказчика отделены от технических трактовок. Архитектура:
[ADR-001](adr/ADR-001.md), [ADR-002](adr/ADR-002.md), [ADR-003](adr/ADR-003.md).

## A. Принятые технические решения

| Решение | Причина | Последствия и компромиссы |
| --- | --- | --- |
| React SPA + Supabase, без собственного backend | небольшой объём, готовые Auth и API | меньше инфраструктуры, часть бизнес-правил и тестов в SQL |
| Права в PostgreSQL | прямой запрос должен быть так же ограничен, как UI | нужны RLS, гранты столбцов и проверки привилегированных функций |
| Критические изменения через SQL RPC | сервер задаёт автора и проверяет переход/назначение | требуется контроль владельцев, search_path и EXECUTE |
| Статус и история в одной транзакции | исключить статус без события | ошибка истории откатывает всю операцию |
| Нет прямого редактирования истории | достоверность событий | пользователь не исправляет аудит; административный доступ — отдельная граница доверия |
| Hard delete + CASCADE | ответ заказчика разрешает удалять связанную историю | нет архива и восстановления средствами UI |
| Переназначение в любом статусе | подтверждено заказчиком | завершённая задача меняет исполнителя, но не открывается заново |
| FOR UPDATE задачи для переходов и назначений | сериализовать конкурентные команды | ожидавший запрос проверяет уже актуальное состояние и может получить отказ |
| Email через ограниченные RPC | имён в схеме нет, auth.users закрыта | email только в доступной задаче; явные проверки доступа надо синхронизировать с RLS |
| QueryClient на пользователя | не показывать кеш предыдущей сессии | после смены сессии бизнес-данные загружаются заново |

## B. Допущения и трактовки требований

### Явно согласовано с заказчиком

- Удаление задачи удаляет историю; удаление объекта — задачи и их историю.
- Переназначение возможно на любом этапе. В реализации это включает `accepted`.
- Возврат на доработку требует комментария — прямое требование исходного ТЗ.
- Только назначенный исполнитель выполняет действия исполнителя; постановщик
  принимает или возвращает результат. Остальные переходы запрещены исходным ТЗ.

### Архитектура и уточнения последующих этапов

- Переназначение не меняет статус и сохраняет историю; это закреплено
  в предоставленной архитектуре и требованиях Stage 5.
- `NULL → new` записывается для новых задач после Stage 5. Старые задачи
  не дополняются вымышленными событиями задним числом.
- Назначить можно только профиль `executor`. У аккаунта одна роль.
- Повторное назначение того же исполнителя успешно, без UPDATE.
- Новый исполнитель видит всю прежнюю историю, включая прошлых участников.

### Самостоятельные технические трактовки

- Нет организаций/тенантов: постановщики видят общую базу и управляют задачами
  друг друга. Авторство не ограничивает права другого постановщика.
- Редактируются название/описание задачи и название/адрес объекта. Перемещение
  задачи между объектами не реализовано; `object_id` не обновляется клиентом.
- Названия и адрес должны содержать непробельный символ. Описание необязательно.
  UI обрезает края названий/адреса, БД запрещает пустоту, но не нормализует строки.
- Комментарий возврата не может состоять только из пробелов, табов и переводов
  строк. UI предлагает комментарий только для возврата; RPC допускает
  необязательный комментарий и для других разрешённых переходов.
- Удаление пользователей с профилем и используемых профилей блокируется RESTRICT.
  Управление аккаунтами и ролями в UI отсутствует.
- Показывается текущий email Auth, а не имя или снимок email на дату события.
  При изменении email подпись старых событий тоже изменится. UUID — резервная подпись.
- История упорядочена по `created_at`, затем `id`; даты показываются в часовом
  поясе браузера. UUID при равном времени обеспечивает стабильность, не порядок commit.

## C. Ограничения и незавершённая работа

Эти улучшения не требовались исходным ТЗ и не считаются его нарушениями:

- Нет Realtime и уведомлений. Переназначение не удаляет уже загруженные данные
  из другого браузера; при новом запросе доступ проверяется заново.
- Нет пагинации, поиска и расширенных фильтров. UI не догружает результаты сверх
  лимита Data API; большие выборки могут быть усечены лимитом сервера.
- Нет журнала переназначений и истории редактирования названия/описания.
- Нет проверки версии при параллельном редактировании обычных полей: последний
  UPDATE может перезаписать предыдущий. Блокировки workflow этого не решают.
- Нет ключа идемпотентности создания задач/объектов. Повтор после потери ответа
  может создать дубликат. UI блокирует повторный клик, но не другие вкладки/клиенты.
- Нет регистрации, сброса пароля, OAuth/MFA и администрирования аккаунтов в UI.
- Нет восстановления удалённых данных через UI. Резервные копии и сроки хранения
  требуют отдельной настройки инфраструктуры.

До релиза остаются проверки и подготовка окружения:

- Прогнать текущую версию тестов после миграций чтения email и выполнить UI smoke.
  Ранее полученные результаты Stage 5 не подтверждают последние изменения.
- Создать Cloud-проект, три демо-аккаунта, 2–3 объекта и задачи разных статусов.
  Локальный seed создаёт только аккаунты.
- Настроить Netlify и SPA fallback; в текущем репозитории конфигурации Netlify нет.
- Оценить предупреждение о размере JS-чанка, ранее наблюдавшееся при build;
  оптимизация сборки не входит в документационный этап.
- Подготовить публичную ссылку и доступ к GitHub, передать демонстрационные пароли
  заказчику отдельно от репозитория и административных ключей.
