# ADR-002: Hard delete и переназначение исполнителя

Дата: 2026-11-05. Статус: правила удаления и переназначения подтверждены заказчиком
и повторены в предоставленной архитектуре; детали реализации БД предложены.
Реализация БД не входит в Foundation.

## Контекст

Клиенту нельзя доверять: запрос может быть отправлен напрямую. Постановщиков и
исполнителей несколько. Заказчик подтвердил: история удаляется вместе с задачей
или объектом; постановщик может переназначить исполнителя на любом этапе.

## Решение 1. Удаление

Используем hard delete с каскадным удалением:

- Удаление объекта удаляет его задачи и историю.
- Удаление задачи удаляет её историю.
- Soft delete не требуется.

## Решение 2. Переназначение исполнителя

Постановщик может изменить исполнителя на любом этапе жизненного цикла задачи:

- Новый исполнитель получает доступ к задаче.
- Предыдущий исполнитель теряет доступ.
- Текущий статус сохраняется.
- История предыдущих переходов сохраняется до удаления задачи.

Доступ к объекту для предыдущего исполнителя сохраняется только при наличии
других назначенных ему задач этого объекта.

## Детали защиты для следующих этапов

- Supabase Auth: вход email/пароль; открытая регистрация отключена в настройках
  сервиса. Учётные записи и роли создаёт администратор вручную, вне клиента.
- `profiles.id` связан с `auth.users.id`; роль `manager` или `executor` хранится в БД.
  Пользователь не может изменить себе роль. Предлагается одна роль на пользователя.
- RLS включается для всех прикладных таблиц. Анонимный доступ закрыт.
- Постановщик видит все объекты, задачи и соответствующую историю, управляет
  объектами и задачами. При создании статус строго `new`, автор — `auth.uid()`;
  автор и дата создания впоследствии неизменяемы.
- Исполнитель читает только задачи с `assignee_id = auth.uid()`, их историю и
  объекты с хотя бы одной такой задачей. Чужие задачи того же объекта скрыты.
- Исполнитель не редактирует поля задачи: доступны только разрешённые переходы.
  Будущая функция перехода получает ID задачи, целевой статус и комментарий,
  сама проверяет пользователя, роль, назначение и текущее состояние.
  Переназначение также выполняется защищённой SQL-функцией через RPC.
- Прямое изменение статуса и назначения через табличный API запрещается
  привилегиями БД. Разрешённый обычный CRUD ограничивается RLS и грантами;
  проверки целостности БД страхуют создание и редактирование задач.
  Проверки в SQL-функциях обязательны независимо от наличия RLS.
- Переходы и переназначения сериализуются блокировкой строки задачи в одной
  транзакции. После переназначения дальнейшие действия доступны новому исполнителю;
  статус и старая история остаются. Бывший исполнитель теряет доступ к задаче.
- История формируется автоматически в той же транзакции триггером БД; actor,
  время и старый/новый статус определяет БД. Прямые INSERT/UPDATE/DELETE истории
  через API запрещены грантами и политиками. Функции с повышенными правами
  должны иметь фиксированный `search_path`, точные проверки и минимальные EXECUTE.
- Удаление задачи постановщиком каскадно удаляет историю, удаление объекта —
  его задачи и их историю. Не применять запретительный триггер удаления истории,
  который ломает согласованный каскад. Прямой API DELETE истории всё равно запрещён.
- Во фронтенд в будущем попадают только URL и публичный publishable/anon-ключ;
  service_role/secret-ключи запрещены в клиенте и репозитории.

## Разрешённые переходы

| Из | В | Кто | Условие |
| --- | --- | --- | --- |
| отсутствие | `new` (Новая) | постановщик | создание |
| `new` | `in_progress` (В работе) | назначенный исполнитель | — |
| `in_progress` | `in_review` (На проверке) | назначенный исполнитель | — |
| `in_review` | `accepted` (Принята) | постановщик | — |
| `in_review` | `rework` (На доработке) | постановщик | непустой после trim комментарий |
| `rework` | `in_progress` | назначенный исполнитель | — |

Другие переходы запрещены, в том числе попытка постановщика взять задачу в работу
вместо исполнителя. Редактирование остальных полей и переназначение разрешены
постановщику в любом статусе, без автоматической смены статуса.

## Предлагаемые допущения

- Создание записывается в историю как `NULL → new`, чтобы видеть начало цикла.
- Нет отдельных организаций/тенантов: все постановщики видят общую базу.
- Назначать можно только пользователя с ролью исполнителя.
- Удаление пользователей и смена их ролей вне объёма; ссылки на автора,
  исполнителя и участника истории предполагают RESTRICT, без потери аудита.
- История содержит только смены статусов, не редактирование полей/назначения.

## Последствия и проверки будущих этапов

Скрытия кнопок недостаточно. Понадобятся интеграционные проверки прямых запросов
под постановщиком, двумя исполнителями и анонимным пользователем: чужое чтение,
все разрешённые/запрещённые переходы, пустой комментарий, подмена автора/роли,
подделка истории, конкурентное переназначение и каскадное удаление. В Foundation
эти гарантии описаны, но не реализованы и не проверены.
