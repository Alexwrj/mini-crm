# ADR-003: Email участников только в контексте доступной задачи

Дата фиксации: 2026-11-05. Статус: реализовано в согласованных доработках Stage 5;
документировано в Stage 6A. Новый прогон тестов после доработок не подтверждён.

## Контекст

Пользователь попросил заменить неудобные UUID автора, исполнителя и участников
истории на email. В profiles есть только id/role, имён нет. Email находится
в закрытой auth.users. Исполнитель не должен получить общий справочник пользователей.

## Решение

Существующая `list_executors()` используется только постановщиком для выбора
исполнителя. Дополнительно реализованы read-only SECURITY DEFINER RPC:

- `read_task(uuid)` — задача и `author_email/assignee_email`;
- `read_task_history(uuid)` — события истории и `actor_email`.

Обе явно проверяют auth.uid, профиль и доступ к задаче: manager либо назначенный
executor. Без доступа возвращается пустой набор. RLS профилей не расширяется,
auth.users не открывается напрямую. Search_path пуст, имена объектов полные,
PUBLIC/anon лишены EXECUTE, authenticated допускается с внутренней проверкой.
История сортируется по created_at/id.

Клиент показывает email, помечает собственные действия «(вы)», при отсутствии
email использует UUID. Подпись берётся из текущего Auth, не хранится в истории.

## Альтернативы

- Хранить публичное имя в profiles: потребовались бы новое поле, заполнение
  и изменение правил чтения; для текущей задачи лишний объём.
- Открыть список всех email: даёт исполнителю данные вне доступной задачи.
- Ограничиться list_executors: executor не вправе вызвать её, и она не возвращает
  постановщиков — авторов и участников приёмки.

## Последствия

Нет отдельного каталога персональных данных или изменения workflow. После
переназначения новый исполнитель видит email прежних участников истории,
старый теряет доступ при новом запросе. При изменении email меняются подписи
старых событий; actor UUID и сама история остаются прежними.

SECURITY DEFINER не полагается на RLS владельца: его проверки дублируют модель
видимости задач. При изменении модели доступа их нужно обновить вместе с policies
и тестами. Администратор/service_role остаются отдельной границей доверия.
