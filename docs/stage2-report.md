# Stage 2 — Database Schema

Дата: 2026-11-05. Stage 1 принят; изменения ограничены схемой и её документацией.

## Реализовано

- Версионированная транзакционная миграция создаёт `profiles`, `objects`,
  `tasks`, `task_status_history` в `public`.
- UUID PK, NOT NULL, CHECK для роли и всех трёх полей статуса.
- Обязательные названия/адреса отклоняют пустые и пробельные строки.
- `created_at DEFAULT now()` у объектов, задач и истории; `status DEFAULT 'new'`.
- Объект → задачи → история: ON DELETE CASCADE. Все ссылки на пользователей
  и профили: ON DELETE RESTRICT.
- Шесть индексов поддерживают FK, список объектов, задачи объекта/исполнителя
  и хронологию истории. PK покрывают остальные уникальные ссылки.
- RLS включён на четырёх таблицах. Policies отсутствуют. У PUBLIC, anon,
  authenticated отозваны все табличные привилегии, включая TRUNCATE.
- Добавлена воспроизводимая проверка на отдельном локальном PostgreSQL-кластере.
  Реальных аккаунтов нет, используются UUID-записи в одноразовой заглушке Auth.

## Выполненные SQL-проверки

Команда: `bash scripts/check-schema.sh` — **exit 0, 173 проверки прошли**.
Среда: PostgreSQL 14.15 (Homebrew), aarch64 macOS. Кластер создан с нуля,
Unix socket без TCP. После проверки PostgreSQL остановлен, временные файлы удалены.
Во время запуска bash сообщил о недоступной локали C.UTF-8; initdb использовал
явные `--no-locale --encoding=UTF8`, проверки завершились успешно.

| Требование | Результат |
| --- | --- |
| Применение миграций с нуля | Четыре таблицы, шесть индексов, четыре ENABLE RLS, REVOKE и COMMIT успешно |
| FK | Все шесть FK отклоняют несуществующую ссылку с SQLSTATE 23503 |

## Известные ограничения

- Полный Supabase Auth/PostgREST и облачная среда не запускались. Проверка
  выполнена в изолированном PostgreSQL с минимальной auth.users и API-ролями.
- CHECK проверяет значения, а не последовательность переходов. Нет принудительного
  initial-new, проверки роли assignee/author, обязательного комментария rework,
  автоматического аудита, защиты времён/автора от администратора и переназначения.
  Эти правила намеренно оставлены следующим этапам; клиентские операции закрыты.
- Владельцы таблиц/суперпользователи обходят обычный RLS. FORCE RLS не добавлен;
  административное подключение необходимо для миграций.
- Не изменяются глобальные default privileges или существующие роли Supabase;
  ограничения доступа применены только к четырём новым таблицам.
- SQL-файл не предназначен для повторного ручного исполнения поверх готовой схемы.
  Повторные применения контролируются механизмом версий миграций.
- Коммиты, деплой, новые пользователи Supabase и переход к Stage 3 не выполнялись.

## Неоднозначности и принятые решения

1. В раннем ERD не было `objects.created_at`, а описание считалось обязательным.
   Текущее задание Stage 2 приоритетно: добавлен created_at, description nullable.
2. Генерация UUID не была определена: у трёх бизнес-таблиц DEFAULT
   gen_random_uuid(); у profiles ID должен совпадать с существующим Auth-пользователем.
3. «Не уничтожать данные при удалении пользователя» реализовано через RESTRICT
   на auth.users → profiles и всех ссылках на profiles. Даже пользователь с профилем
   без задач требует сначала явного удаления своего профиля администратором.
4. Пустые обязательные строки включают строки из пробелов, табов и переводов строк
   по POSIX-классу whitespace. Строки не нормализуются автоматически.
5. Nullable from_status допускается без привязки к созданию. Проверка смысла
   перехода и комментария — workflow, который этот этап явно исключает.
6. Не добавлены ограничения роли исполнителя/автора по FK: обычный FK подтверждает
   существование профиля, а проверка его роли относится к будущей бизнес-логике.

Решения не требуют изменения предоставленной архитектуры.

## Ручной smoke checklist

1. Убедиться, что initdb, pg_ctl и psql одной версии PostgreSQL 14+ доступны в PATH.
2. Выполнить `bash scripts/check-schema.sh` обычным пользователем. Ожидать 173
   успешные проверки, ROLLBACK, exit 0 и сообщение об удалении временного кластера.
3. Перед будущим применением в локальном Supabase проверить наличие auth.users
   и ролей anon/authenticated; применять только файл из migrations, не bootstrap.
4. В SQL Editor после применения проверить `pg_tables.rowsecurity` для четырёх
   таблиц, пустой список `pg_policies` для них и отсутствие клиентских привилегий.
5. Под anon/authenticated запросы таблиц должны завершаться permission denied;
   не выдавать права и не добавлять policies ради работы пока ещё пустого клиента.
6. Тесты каскадов/FK/некорректных значений повторять только в изолированной базе
   с откатом. Не использовать реальные клиентские записи для smoke.

Основной тестовый скрипт уже покрывает пункты 4–6 в одноразовой среде.
