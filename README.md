# Мини-CRM «Объекты и задачи»

**Для заказчика: [как работает система, роли и защита данных](docs/system-overview.md).**

## О проекте

CRM строительной компании. Постановщик создаёт
объекты и задачи, назначает исполнителей и принимает результат. Исполнитель
выполняет назначенные задачи и отправляет их на проверку. Stage 1–5 реализованы
и приняты; Stage 6A готовит документацию, без публикации демо.

## Реализованные возможности

**Постановщик:** видит все объекты и задачи, создаёт, редактирует и удаляет их;
выбирает исполнителя, принимает результат либо возвращает с обязательным
комментарием. Переназначение доступно в любом статусе, включая «Принята»,
и сохраняет статус и историю.

**Исполнитель:** видит только назначенные задачи и объекты с такими задачами;
берёт задачу в работу, отправляет на проверку, возвращает в работу после замечаний.
Не редактирует поля задач и не управляет объектами или назначениями.

Обе роли видят историю доступных задач. Автор, исполнитель и участники истории
отображаются по текущему email; UUID используется, если email отсутствует.
Есть вход по email/паролю, восстановление сессии и выход. Регистрации в UI нет.

| Из статуса | В статус | Кто |
| --- | --- | --- |
| создание | Новая (`new`) | постановщик |
| Новая | В работе (`in_progress`) | назначенный исполнитель |
| В работе | На проверке (`in_review`) | назначенный исполнитель |
| На проверке | Принята (`accepted`) | постановщик |
| На проверке | На доработке (`rework`) | постановщик, с непустым комментарием |
| На доработке | В работе | назначенный исполнитель |

Другие переходы запрещены; «Принята» — конечный статус.

## Технологии

| Компонент | Назначение |
| --- | --- |
| React + TypeScript + Vite | SPA, типизация и сборка |
| React Router | навигация |
| TanStack Query | запросы, кеш и обновление бизнес-данных |
| Supabase SDK + Auth | вход, сессия, обращения к API |
| PostgREST + PostgreSQL | API, данные, ограничения и транзакции |
| RLS + SQL RPC | серверные права и защищённые операции |
| Tailwind CSS v4 + shadcn/ui (Radix) | стилизация и базовые компоненты |
| ESLint + Vitest + Testing Library | статические проверки и UI-тесты |

Версии зависимостей зафиксированы в [package-lock.json](package-lock.json).

## Архитектура

React SPA обращается к Supabase Auth для входа и к PostgREST для данных/RPC.
PostgreSQL проверяет права через RLS и гранты столбцов; SQL RPC проверяют
критические операции. Отдельного собственного backend нет. Проверки React Router
и скрытие кнопок служат UX и не заменяют ограничения базы.

AuthProvider хранит сессию и профиль; роль берётся из `profiles`, а не из email
или редактируемых метаданных. Для текущего пользователя создаётся отдельный
QueryClient; при выходе запросы отменяются, кеш очищается. Кеш бизнес-данных
не сохраняется в localStorage; сама Auth-сессия сохраняется Supabase SDK.

[ADR-003](docs/adr/ADR-003.md), [C1](docs/c1.md), [C2](docs/c2.md),
[ERD](docs/erd.md), [модель безопасности](docs/security-model.md).

## Локальный запуск

Нужны Node.js **24.12.0** ([.nvmrc](.nvmrc)), npm и запущенный Docker.
Supabase CLI входит в devDependencies. Команды выполняются из корня проекта.
API использует порт 54321, БД — 54322; порты должны быть свободны.
При конфликте сначала выясните владельца порта, не останавливайте чужой процесс вслепую.

### 1. Установка зависимостей

```sh
nvm use
npm ci
```

Если nvm не установлен, выберите указанную версию Node другим способом.

### 2. Запуск локального Supabase

```sh
npx supabase start
```

Если стек работал со старой конфигурацией Auth, сначала выполните
`npx supabase stop`, затем снова start. В текущем
[config.toml](supabase/config.toml) отключены регистрация и SQL seed.

### 3. Применение миграций

```sh
npx supabase migration up
```

Применяются все версии из [supabase/migrations](supabase/migrations), включая
RPC чтения email. Для **одноразовой локальной базы** вместо этой команды можно
использовать `npx supabase db reset`: он удаляет локальные данные. После reset
снова создайте аккаунты. Не используйте remote/linked-флаги в локальных инструкциях.

### 4. Создание тестовых аккаунтов

```sh
npm run auth:seed
```

Скрипт использует локальный Auth Admin API и создаёт `profiles`. Повторный запуск
не дублирует пользователей и использует сохранённые пароли. Он восстанавливает
тестовые роли и пароли этих трёх аккаунтов; запускайте его осознанно.
Административный ключ берётся из локального CLI, не из frontend env. Скрипт
принимает только локальный HTTP API с портом из конфигурации, не Cloud.

### 5. Настройка frontend

Seed формирует `.local/frontend.env` с публичной конфигурацией:

```sh
cp .local/frontend.env .env.local
```

Альтернатива — скопировать [.env.example](.env.example) и заполнить обе переменные
публичными значениями своего локального Supabase:

```dotenv
VITE_SUPABASE_URL=http://127.0.0.1:54321
VITE_SUPABASE_PUBLISHABLE_KEY=
```

Пустой ключ в образце намеренный. Нужен publishable или legacy anon-ключ;
секретные/административные ключи запрещены. Любое значение `VITE_*` попадает
в браузерную сборку. Не публикуйте полный вывод CLI с административными ключами.

### 6. Запуск React-приложения

```sh
npm run dev
```

Откройте адрес из вывода Vite, обычно `http://localhost:5173`. После изменения env
перезапустите Vite. Для просмотра сборки: `npm run build`, затем `npm run preview`
(это локальный просмотр, не production-сервер).

## Тестовые аккаунты

| Логин | Роль |
| --- | --- |
| `manager@mini-crm.test` | постановщик |
| `executor-a@mini-crm.test` | исполнитель A |
| `executor-b@mini-crm.test` | исполнитель B |

Случайные локальные пароли доступны владельцу компьютера в `.local/auth-users.json`.
Этот файл и `.env.local` исключены из Git. Не публикуйте JSON, токены и
административные ключи. Seed не создаёт объекты и задачи — подготовьте их через UI.
Для Cloud нужны отдельные демонстрационные аккаунты; локальный seed туда не запускают.

## Проверки

Это команды для запуска, **не подтверждение прохождения текущей версии**.
После последних изменений email нужен новый прогон перед релизом.

| Команда | Назначение |
| --- | --- |
| `npm run typecheck` | TypeScript |
| `npm run lint` | ESLint, предупреждения считаются ошибками |
| `npm test` | Vitest, один прогон |
| `npm run test:watch` | Vitest в watch-режиме |
| `npm run build` | production build в `dist/` |
| `npm run check` | typecheck → lint → tests → build |
| `npm run test:auth-isolated` | реальные JWT/Auth, историческая схема Stage 3A |
| `npm run test:crud-isolated` | реальные JWT/CRUD, историческая схема Stage 3B + 4 |
| `npm run test:workflow-isolated` | все текущие миграции с нуля, CRUD + workflow + чтение email |
| `npm run test:auth-api` | Auth на уже запущенном локальном проекте |
| `npm run test:crud-api` | CRUD на уже запущенном локальном проекте |

Изолированные проверки требуют Docker. Они поднимают отдельные проекты на портах
5632x (Auth), 5732x (CRUD), 5832x (Workflow), сбрасывают только свою тестовую БД
и останавливают её с удалением данных. Не запускайте несколько экземпляров одного
режима одновременно. Workflow использует SQL в одноразовом контейнере для проверки
владельцев, блокировок и отката. Обычные операции проверяются настоящими JWT.

`test:auth-api` и `test:crud-api` создают/восстанавливают тестовые аккаунты текущего
локального проекта и меняют их metadata; CRUD создаёт и удаляет свои fixtures.
Для безопасной регрессии предпочтительны изолированные команды. Тесты не заменяют
ручную проверку UI. `bash scripts/check-schema.sh` — дополнительная историческая
проверка **только** схемы Stage 2; требует `initdb`, `pg_ctl`, `psql`, не проверяет
актуальные RPC/RLS. Bootstrap из [supabase/tests](supabase/tests) нельзя применять
к рабочему Supabase: он предназначен только для пустого одноразового PostgreSQL.

## Маршруты и структура

| URL | Назначение |
| --- | --- |
| `/login` | email/password |
| `/objects` | доступные объекты |
| `/objects/:objectId` | объект и доступные задачи |
| `/tasks/:taskId` | задача, workflow, назначение, история |
| `/my-tasks` | задачи текущего исполнителя |

После входа manager попадает на `/objects`, executor — на `/my-tasks`.
Корень `/` выполняет такой же выбор; неизвестный маршрут показывает 404.
При восстановлении сессии нет преждевременного редиректа. Отсутствующий профиль
блокирует защищённые экраны. Все постановщики работают с общей базой, организаций нет.

- [src/app](src/app) — маршруты, провайдеры, тема.
- [src/features/auth](src/features/auth) — сессия, профиль, route guards.
- [src/features/crm](src/features/crm) — API, query hooks, CRUD и workflow UI.
- [src/pages](src/pages), [src/components/ui](src/components/ui) — экраны и shadcn/ui.
- [supabase/migrations](supabase/migrations) — все изменения БД.
- [scripts](scripts) — аккаунты и проверки.

## Стилизация

Tailwind CSS v4 подключён официальным Vite-плагином. Тема и глобальные правила —
в [globals.css](src/app/globals.css), компонентные стили — utility-классы в JSX.
shadcn/ui настроен в [components.json](components.json); используются Button,
Input, Card, Badge, Table, Dialog, Select, Label. Alias `@/` одинаков в Vite
и TypeScript. Отдельного слоя UI-библиотеки и тёмной темы нет.
